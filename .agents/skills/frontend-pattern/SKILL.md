# Frontend Pattern (`frontend/`)

The React SPA in `frontend/` talks to the Go core over Connect RPC (same origin, `/api`,
cookie session). It is built into `dist/` and embedded into the core binary. Where each package
lives and how codegen flows into `src/api/schemas` and the `proto` package is covered in the
**project-pattern** skill. This skill covers the code inside `frontend/src`.

The architecture deliberately **mirrors core-pattern**: same composition root, same
one-folder-per-feature layout, same "every feature has every layer" rule, same single public
wiring point, and lint-enforced import boundaries. If you know `core/`, use the map below to find
the matching place here. It is not a 1:1 port: there is no service layer, no domain/mapper layer,
and no error-wrapping chain, because the browser has different jobs (rendering, caching, forms,
navigation).

## Stack

| Concern | Choice |
|---|---|
| Build / dev | Vite, `#/*` → `src/*` import alias (use `#/`, not `@/`) |
| Routing | TanStack Router, file routes in `src/routes/` → generated `routeTree.gen.ts` |
| RPC client | `@connectrpc/connect-query` on TanStack Query; generated `proto/servicesV1` (services) and `proto/modelsV1` (messages) |
| Server state | TanStack Query cache (`app/query-client.ts`); no global client-state store |
| UI | Mantine (`@mantine/core`, `notifications`, `modals`) |
| Forms | react-hook-form + `zodResolver`; zod bodies generated by orval in `src/api/schemas/` |
| Errors | `ConnectError` → `getErrorMessage` (`shared/lib/errors.ts`) → `<Alert>` / notification |
| Tests | vitest, `src/**/*.test.ts` next to the code |
| Lint / fmt | oxlint (`frontend/.oxlintrc.json`, includes the import boundaries), oxfmt |

## core ⇄ frontend map

| core (`core/internal/`) | frontend (`frontend/src/`) | Role |
|---|---|---|
| `app/` (deps, server, mux) | `app/` (`providers.tsx`, `query-client.ts`, `transport.ts`) + `main.tsx`, `router.tsx` | Composition root: builds infra once |
| `app/handler.go` `RegisterConnect` | `routes/<path>.tsx` | Thin registration: path → feature entry point + guard |
| `features/<feature>/` | `features/<feature>/` | One folder per feature, same singular name |
| `handler.go` | `pages/<name>-page.tsx` | Entry point: composes components, navigates on success |
| — (no equivalent) | `components/` | Rendering, forms, local UI state |
| `repository.go` | `api/use-<feature>-<op>.ts` | Data access: the RPC call + its cache reads/writes |
| `service.go` | — | No frontend counterpart; business rules belong to core |
| `types.go` + validation tags | `schemas.ts` | Orval zod body extended with UI messages |
| `mapper.go` | — | Proto messages *are* the frontend's domain types; no mapper |
| `access.go` (`AccessPolicy`) | `guards.ts` | Route `beforeLoad` guards (`requireAuth`, `redirectIfAuthed`) |
| `provider.go` (`Deps` + `Provide`) | `index.ts` | Single public surface; the only thing other code imports |
| `errors.go` → herodot → Connect | `shared/lib/errors.ts` `getErrorMessage` | The far end of core's error flow |
| `helper/` | `shared/` (`components/`, `lib/`) | Cross-feature infra that knows no feature |
| `db/sqlc/` (generated) | `api/schemas/`, `routeTree.gen.ts` (generated) | Never edit by hand |
| `depguard` in `.golangci.yml` | `no-restricted-imports` overrides in `.oxlintrc.json` | Boundary enforcement |

## Directory Layout

```
frontend/src/
├── main.tsx              # mounts <Providers><RouterProvider/></Providers>
├── router.tsx            # createRouter: context { queryClient, transport }
├── app/                  # composition root: Providers, queryClient, Connect transport
├── routes/               # file routes; thin, import only from #/features/<feature>
├── routeTree.gen.ts      # generated from routes/, never edit
├── api/schemas/          # orval zod output from openapi.json, never edit
├── shared/
│   ├── components/       # feature-agnostic UI (e.g. devtools)
│   └── lib/              # feature-agnostic helpers (e.g. errors.ts)
└── features/<feature>/   # one folder per feature (see below)
```

## Feature Module Layout

```
features/<feature>/
├── api/
│   └── use-<feature>-<op>.ts   # one file per RPC: hook + that RPC's key/set/fetch helpers
├── components/                 # <name>.tsx: forms, lists, modals, feature layout
├── pages/                      # <name>-page.tsx: what a route renders
├── schemas.ts                  # form schemas (orval body .extend(...)) + z.input types
├── schemas.test.ts             # schema tests (and other *.test.ts next to their code)
├── guards.ts                   # optional: route beforeLoad guards
└── index.ts                    # public API: only what routes/other features may use
```

Files are kebab-case. Not every feature has every folder: `layout` has no `api/` or `pages/`
because it renders the app chrome and owns no RPCs. A feature that calls an RPC always has the
`api/` hook for it, though (see below).

## Layer Rules

```
routes/<path>.tsx ── createFileRoute: beforeLoad guard + component from #/features/<feature>
   │
   ▼
page              ── composes components, owns navigation (useNavigate) on success
   │
   ▼
component         ── renders, holds form/UI state, calls api hooks, shows errors + notifications
   │
   ▼
api hook          ── useQuery/useMutation(<Feature>Service.method.<op>), cache set/invalidate
                     in onSuccess; knows nothing about Mantine, forms or the router
```

| Layer | May import | Must NOT import |
|---|---|---|
| `routes/` | `@tanstack/react-router`, `#/features/<x>` (index only) | a feature's internals |
| `pages/`, `components/` | own `../api`, `../schemas`, `../components`, Mantine, router, `proto/modelsV1` types, `#/shared`, `#/features/<x>` | `@connectrpc/connect-query`, `proto/servicesV1` |
| `api/` | connect-query, `@tanstack/react-query`, `proto/*`, `@bufbuild/protobuf`, sibling `api/` files | `@mantine/*`, `react-hook-form`, `@tanstack/react-router` |
| `shared/` | libraries, other `shared/` | any `#/features/*` |
| feature → feature | `#/features/<x>` (its `index.ts`) | `#/features/<x>/...` deep paths, `../../<x>` relative paths |

All of these are enforced by `no-restricted-imports` overrides in `frontend/.oxlintrc.json`
(`task frontend:lint:check`), the way `depguard` enforces core's boundaries. As in core, a few
rules stay a review matter because lint only sees import specifiers:

- Inside a feature use relative imports (`../api/use-note-list`). Never import your own
  `#/features/<self>` index, because that creates cycles.
- Cross-feature imports go one way. If two features need each other, the shared piece belongs in a
  third feature (as `layout` composes `auth`), not in `shared/`.
- `guards.ts` and `schemas.ts` sit at the feature root and follow the `api/` spirit: no UI.

### Every RPC has an api hook, even a pass-through

Components never call `useQuery(NoteService.method.noteGet, ...)` directly, even when the hook
would be one line. This is the frontend twin of core's pass-through service rule: consistency
beats saving three lines, the hook is where cache updates land when they are needed later, and
there is no per-RPC judgment call to repeat. Do not inline a hook to "simplify".

### Naming: one name per RPC across every layer

The hook is `use` + the RPC name, and the file is its kebab-case form. One grep for `NoteList`
then finds the TypeSpec op, the Go handler method, and the frontend hook.

| RPC | File | Hook | Helpers in the same file |
|---|---|---|---|
| `AuthMe` | `api/use-auth-me.ts` | `useAuthMe` | `authMeQueryKey`, `setAuthMe`, `fetchAuthMe` |
| `AuthLogin` | `api/use-auth-login.ts` | `useAuthLogin` | — |
| `NoteList` | `api/use-note-list.ts` | `useNoteList` | `noteListQueryKey` |
| `NoteCreate` | `api/use-note-create.ts` | `useNoteCreate` | — |

Pages are `<Name>Page` in `pages/<name>-page.tsx`. Form schemas are `<op>Schema` plus a
`<op>SchemaTypes = z.input<...>` type.

## api hook shapes

```ts
// Query: select unwraps `data` (core responses always wrap the payload in data).
// Keep the whole response instead when the UI also needs `pagination`.
export function useNoteList() {
  return useQuery(NoteService.method.noteList, {}, { select: (res) => res.data });
}

// Mutation: keep the cache right in onSuccess, so components never touch queryClient
export function useNoteCreate() {
  const queryClient = useQueryClient();
  return useMutation(NoteService.method.noteCreate, {
    onSuccess: () => queryClient.invalidateQueries({ queryKey: noteListQueryKey() }),
  });
}
```

Cache rules:

- When the response carries the new entity and one cached query shows it, **set** it
  (`setAuthMe` after login/update). When it affects lists, **invalidate** the list key.
  Logout **clears** the whole cache.
- Build keys with `createConnectQueryKey({ schema, cardinality: "finite" })`. Omitting `input`
  matches every input of that RPC.
- For data a guard or loader needs outside React, export `fetch<Feature><Op>(queryClient,
  transport)` that uses `queryClient.query(createQueryOptions(...))`, like `fetchAuthMe`.
- `queryClient` defaults are `retry: false` and `refetchOnWindowFocus: false`. Do not override
  them per hook without a reason.

## Adding a Feature: Checklist

1. **Contract and codegen:** follow project-pattern (TypeSpec → `task gen:api`). This gives you
   `<Feature>Service` in `proto/servicesV1`, messages in `proto/modelsV1`, and zod bodies in
   `src/api/schemas/<tag>/`.
2. **Folder:** `features/<feature>/` with the same singular name as `core/internal/features/<feature>`.
3. **api/:** one `use-<feature>-<op>.ts` per RPC the UI calls, with cache updates in `onSuccess`.
4. **schemas.ts:** extend the orval body for each form with user-facing messages, and add a
   `schemas.test.ts`.
5. **components/ and pages/:** forms follow
   [references/forms-and-errors.md](references/forms-and-errors.md). Wrap signed-in pages in
   `AppShell` from `#/features/layout`.
6. **index.ts:** export pages, guards, and only the hooks/components other features need.
7. **Route:** `routes/<path>.tsx` with `createFileRoute`, `beforeLoad: requireAuth` for
   signed-in pages, and `component` from `#/features/<feature>`. The Vite plugin regenerates
   `routeTree.gen.ts`. Without the dev server, run `pnpm --filter frontend generate-routes`.
8. **Verify:** `pnpm --filter frontend typecheck`, `task frontend:test`,
   `task frontend:lint:check`, `task frontend:fmt:check`.

A complete worked example (`note`: list, create, delete) is in
[references/reference-feature-note.md](references/reference-feature-note.md). Read it before
writing a new feature. Read `features/auth` second for guards, cache `set`, and `fetch*`.

## Frontend Rules (summary)

- Routes are thin: guard + component, no JSX logic and no data fetching beyond the guard.
- Every RPC call goes through `api/use-<feature>-<op>.ts`, and only `api/` imports
  connect-query or `proto/servicesV1`.
- Proto messages flow straight into components (`proto/modelsV1` types). Do not add mapper or
  view-model layers.
- Business rules live in core. The frontend validates for UX (zod) and trusts the server's errors.
- Show server errors with `getErrorMessage(error)`. Never parse Connect error details in a component.
- Navigation on success belongs to the page (pass `onSuccess` into the form). Notifications for
  in-place actions belong to the component.
- Never edit `api/schemas/` or `routeTree.gen.ts`. Change the source and regenerate.
- `shared/` knows no feature. Features talk only through `index.ts`.
